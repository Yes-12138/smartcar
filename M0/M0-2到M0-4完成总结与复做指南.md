## M0-2：两列数据的相关系数

原程序在样例上算出 `r = 0.00015648828136792707`。我修了分母：先分别计算两列与各自平均值之差的平方和 `dx`、`dy`，再用 `sqrt(dx * dy)` 作分母。分子是对应离差相乘后的总和。修正后样例的 `r = 0.5634747254524841`，表示两列有一定的正线性关系；它不证明一列造成了另一列变化。

程序现在分开做三件事：读 YAML 配置、读 CSV 数据、计算 `r`。配置里填 CSV 路径和两列的表头。缺文件、缺列、空数据、非数字、某列完全不变时会给可读错误。10 个测试已在 VM 上通过。

我复做时先运行：

```bash
cd ~/smartcar-assessment
./.venv/bin/python M0/M0-2/legacy_corr.py --config M0/M0-2/config.yaml
./.venv/bin/python -m unittest discover -s M0/M0-2/tests -v
```

`cd` 是切换目录；`./.venv/bin/python` 是指定本仓库的 Python 虚拟环境；`-m unittest discover` 是让 Python 自动寻找并运行测试。这里的 `-s` 后面是测试目录，`-v` 会把每个测试名打印出来。

**我应该会回答：** 为什么要开平方？因为分母要把两列的离差平方和还原成同一量纲；只用 `dx * dy` 会把结果压得过小。为什么常数列不能计算？因为它的离差平方和是 0，分母变成 0。

## M0-3：清洗传感器数据

原程序不是只错了一处。先遇到 CSV 列名大小写不对，接着是输出路径写到了不存在的 `/out`，再往下还有标准差、筛选和输出内容的问题。我在 [M0-3 README](https://github.com/Yes-12138/smartcar/blob/main/M0/M0-3/README.md) 里按原文件位置记了 8 个缺陷和对应改法。

最需要理解的三点：

1. **标准差**：每个值减均值，先平方再相加，除以数据个数，最后开平方。直接把离差相加会相互抵消，得到接近 0 的假结果。这题采用总体标准差，除以 `n`。
2. **找异常值**：判断 `abs(value - mean) > 2 * std`，这样高得离谱和低得离谱的值都能找到。均值和标准差先用全部原始数据算，再筛选。
3. **保存整行**：不要一边遍历列表一边删元素，否则相邻异常值可能漏掉。新建一个列表放保留的行，并同时写出 `time,value` 两列。

样例有 60 行数据，原始均值 `50.431536666666666`，总体标准差约 `18.50327949328593`；删除 `5.80`、`5.90`、`6.00` 三个时间对应的异常值，输出剩 57 行数据。8 个测试已在 VM 上通过。

```bash
cd ~/smartcar-assessment/M0/M0-3
../../.venv/bin/python sensor_analyzer.py --input sensor_data.csv --output /tmp/m0-3-my-check.csv
../../.venv/bin/python -m unittest discover -s tests -v
```

`--input` 指要读的 CSV，`--output` 指结果写到哪里。这里放在 `/tmp`，练习时不会覆盖仓库里已提交的 `cleaned_data.csv`。可以再用 `head /tmp/m0-3-my-check.csv` 看前几行，用 `wc -l /tmp/m0-3-my-check.csv` 数行数；应有 58 行，因为还包括 1 行表头。

## M0-4：按依赖执行任务

任务表里，`dependencies` 写的是“做当前任务以前，哪些任务必须成功”。例如 `Init → Navigate`；`Navigate` 后分成 `DetectQR` 和 `AvoidObstacle` 两路；`Place` 要等 `Grasp` 和 `AvoidObstacle` 两项都成功。这种先后关系用拓扑排序处理：先找没有前置任务的项目，完成排序后再让它的后继进入候选队列。出现 A 等 B、B 又等 A 的环时，谁都不能先开始，所以配置报错。

每项任务按 `success_rate` 随机判断结果，最多尝试 3 次（首次 + 2 次重试）。三次都失败记 `FAILED`，依赖它的任务记 `SKIPPED`，其他独立任务仍可继续。`--seed 42` 固定随机数，方便重复检查。每次尝试会真实等待 `duration` 秒；总时限到了，正在做的和未开始的任务记 `TIMEOUT`。正常结束退出码是 0，超时是 2，配置或文件错误是 1。

```bash
cd ~/smartcar-assessment/M0/M0-4
../../.venv/bin/python scheduler.py --config tasks_demo.yaml --timeout 15 --report /tmp/m0-4-my-report.json --seed 42
../../.venv/bin/python -m unittest discover -s tests -v
```

`--config` 选 YAML/JSON 任务表；`--timeout` 是整次运行最多多少秒，会覆盖配置里的值；`--report` 选报告保存位置；`--seed` 固定抽签顺序。示例实际运行时 7 项都成功，总耗时约 11.02 秒。报告中有总耗时、是否超时，以及每项任务的最终状态、尝试次数、实际耗时和起止时间。10 个测试已在 VM 上通过。

要专门看超时，可以再运行：

```bash
../../.venv/bin/python scheduler.py --config tasks_demo.json --timeout 1 --report /tmp/m0-4-timeout.json --seed 42
```

我在 VM 上看到 `Init` 成功、`Navigate` 中途超时，其余任务被标记超时。退出码 2 是这次演示预期的结果。`--timeout 1` 并不会让一项原本要花 2.5 秒的任务继续睡到结束。

## 我自己检查作业和提交的方法

```bash
cd ~/smartcar-assessment
git status
git log --oneline -12
git remote -v
```

`git status` 看有没有没提交的改动；`git log --oneline -12` 看最近 12 次提交；`git remote -v` 确认远程地址属于自己的仓库。上面三个命令只查看，不会修改文件。

如果我以后自己修改了一小处，先看 `git diff`，确认没有误改，再按文件提交：

```bash
git diff
git add M0/M0-4/README.md
git commit -m "docs: clarify M0-4 notes"
git push origin main
```

`git add` 把指定文件放进暂存区，`git commit` 给这次改动留一个记录，`git push` 才把本地提交上传到 GitHub。这里的文件路径和提交说明只是示范，必须换成我实际改过的内容；没有修改时不需要再提交。交作业前再运行 `git status`，确认工作区干净。
